# 23 · 无人值守实例续签与断点恢复

状态：2026-10-27，M1 增量；完整 M0–M4 目标与退出条件不变。

## 从手动轮换到两步续签

21 的用户控制面继续负责首次登记、手动轮换与撤销。本轮新增 `services/credentials`、独立 `InstanceCredentials` RPC 和本地 `instancerenew` 客户端，允许已有受管实例用当前证书续签。服务从 mTLS 注册表提取身份，正文没有任意实例/用户选择字段。

直接签发后立即停用旧证书会产生锁死窗口：服务端已轮换，但响应丢失，实例拿不到新证书且旧证书已无效。因此采用两步流程：

1. **PrepareRenewal**：当前证书认证，新密钥 CSR 证明持有权；按请求 ID 保存候选证书，旧证书继续工作。
2. **ActivateRenewal**：只接受该候选证书的新密钥认证；同事务新增历史、替换当前指纹、递增版本、退役旧证书并写审计。

候选证书仅能调用精确的激活方法，不能获得普通工作身份或角色。准备权限最长五分钟且不超出新证书到期时间；可以覆盖旧证书自然到期后的短暂恢复窗口，但所有者撤销/轮换或主体停用立即阻断激活。锁顺序为实例 → 续签记录 → 公钥独占；实例锁及公钥占用锁等待后复核证书/准备期限。

迁移 010 增加 `credential_renewals`，每实例只有一个 pending 请求。公钥守卫横跨手动签发历史与准备记录，阻断同一密钥在两个入口复用。手动轮换仍可覆盖一个尚未激活的准备请求，旧准备随后失效；撤销不能被续签恢复。

## 客户端持久状态

`instancerenew -watch` 按证书剩余寿命提前续签，瞬态失败重试原请求。私钥只在工作实例本地生成；发送内容只有签名 CSR。持久日志绑定目标服务、信任配置、原指纹、实例、版本与请求 ID，使用 OS 文件锁排除同一状态目录的并发写者。

| 停止位置 | 本地/服务端事实 | 恢复动作 |
|---|---|---|
| Prepare 前 | 新私钥/CSR 已落盘 | 原请求继续 Prepare |
| Prepare 回包丢失 | 服务有原候选证书，旧证书仍有效 | 原请求取回完全相同证书 |
| Activate 前 | 新私钥与候选证书已落盘 | 用新密钥继续 Activate |
| Activate 已提交、回包或本地发布失败 | 新证书已是当前凭证，日志保留新密钥 | 用新证书幂等恢复后发布 |
| 准备权限已过期、旧凭证仍有效 | 尚未激活 | 旧凭证确认 Abandon 后才生成新请求/新密钥 |
| 两个凭证都不可用或所有者已撤销 | 不能自助恢复 | 保留日志，走用户控制面恢复 |

发布采用单个证书链+私钥 PEM bundle 的完整替换，避免两文件错配。Windows 与 Unix 使用各自文件替换/锁实现；本轮验证进程终止与写失败恢复，不声明任意硬件断电保证。业务客户端应重载 bundle 并重新连接；本客户端不会自动改写其他工作进程的 TLS 配置。

## 验证范围

服务用例覆盖两步认证隔离、精确重传、旧钥不能激活、新钥激活前不能提交任务、同请求改参、公钥跨表复用、并发准备/激活、撤销/手动轮换/准备过期、审计回滚、锁等待中撤销、等待公钥锁后过期，以及旧证书自然过期后的有界激活。

实际 `anetd` 进程加载签发 CA 并完成续签；实际 `instancerenew` 进程覆盖激活前 OS Kill、激活提交后本地发布失败、重启恢复和 watch 到期触发。恢复后用同一新密钥完成 TCS 接纳。另有过期准备的安全放弃/重新续签和本机文件替换/进程锁验证。

最终通过 **33 项 runner 检查、103 项数据库集成测试、7 项单测**，`go vet ./...` 与 11 个生成绑定文件漂移检查通过；计数排除 3 个子进程辅助入口。CLI 与文件锁测试另通过 Linux 交叉编译，未在 Linux 运行。证据见 [`test/evidence/2026-10-27/renewal`](../../test/evidence/2026-10-27/renewal/)。
